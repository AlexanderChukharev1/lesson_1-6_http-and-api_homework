# Домашняя работа 6. API-витрина

## Задача

Разработайте frontend-клиент для собственного учебного REST API. Приложение должно показывать коллекцию объектов и позволять добавить новый объект через форму.

На семинаре путь данных уже был пройден на готовой странице:

```text
db.json → json-server → GET → Response → JSON → DOM
форма → FormData → объект → JSON → POST → db.json → повторный GET
```

В домашней работе нужно самостоятельно перенести этот путь в другую предметную область, спроектировать данные и довести интерфейс до законченного состояния.

Ориентир по времени — **3–4 часа**. Сначала сделайте обязательную часть на 5 баллов. Дополнительная часть предназначена для исследования новых возможностей и может принести еще 5 баллов.

## Итоговый продукт

Выберите одну понятную тему. Например:

- афиша мероприятий;
- каталог книг или фильмов;
- список туристических маршрутов;
- база учебных встреч;
- каталог вакансий или стажировок;
- собственный вариант.

У приложения должен быть один основной ресурс с осмысленным названием во множественном числе: например, `events`, `books` или `routes`. Название `items` оставлено в стартере только как заглушка и в готовой работе не используется.

Каждый объект ресурса содержит минимум четыре содержательных свойства. `id` в эти четыре свойства не входит. Поля должны влиять на карточку или поведение интерфейса, а не существовать только ради количества.

Пример масштаба модели, но не готовая схема:

```json
{
  "id": "1",
  "title": "...",
  "category": "...",
  "date": "...",
  "capacity": 20
}
```

Не копируйте этот объект буквально — подберите свойства под свою тему.

## Границы работы

В обязательной части используются только механизмы, разобранные на занятии:

- npm только для запуска готового `json-server`;
- `db.json` как источник данных;
- `GET` и `POST`;
- `fetch`, `async/await`, `response.ok` и `response.json()`;
- `FormData`, `JSON.stringify` и DOM;
- состояния загрузки, результата, пустого списка и ошибки;
- Console и Network для диагностики.

Фреймворки, сборщики и готовые UI-библиотеки не нужны. Дополнительный backend-код на Node.js писать не требуется.

### 1. Ресурс и учебный API — до 0,75 балла

В `backend/`:

- ресурс имеет осмысленное название во множественном числе;
- в `db.json` есть минимум три собственные стартовые записи;
- каждая запись содержит минимум четыре содержательных свойства помимо `id`;
- типы значений соответствуют смыслу данных: числа и логические значения не подменены строками без причины;
- `npm install` создает `package-lock.json`, а `npm run dev` запускает API;
- URL ресурса открывается в браузере и возвращает JSON.

Проверка: остановите и снова запустите API, затем откройте endpoint напрямую. Он должен вернуть актуальные данные без участия frontend.

### 2. Загрузка коллекции через `GET` — до 1 балла

Frontend:

- хранит endpoint в одной понятной константе;
- запускает загрузку после открытия страницы;
- вызывает `fetch` с методом `GET` явно или использует его значение по умолчанию;
- проверяет `response.ok` до разбора тела;
- получает данные через `await response.json()`;
- передает полученный массив отдельной функции отображения;
- не содержит копию объектов из `db.json` внутри JavaScript.

Проверка: измените одну стартовую запись непосредственно в `db.json` и обновите страницу. Изменение должно появиться в интерфейсе.

### 3. Состояния и вывод в DOM — до 1 балла

Пользователь видит не только успешный результат, но и ход запроса:

- во время запроса показано состояние загрузки;
- непустой массив превращается в карточки или строки списка;
- карточка показывает все выбранные свойства объекта;
- пустой массив показывает отдельное пустое состояние;
- ошибка сети или HTTP показывает понятное сообщение без падения страницы;
- кнопка повторной загрузки действительно выполняет новый `GET`;
- одновременно показано только актуальное состояние.

Пользовательские значения выводятся безопасно через `textContent` или создание DOM-узлов. Не вставляйте ответы API в `innerHTML`.

Проверка: последовательно проверьте обычный ответ, пустой массив и временно неверный URL. После возврата правильного URL кнопка повтора должна восстановить список.

### 4. Создание записи через `POST` — до 1,25 балла

Форма соответствует выбранной модели и содержит элементы для всех обязательных свойств.

Нужно:

- связать поля с `label` и задать им понятные `name`;
- применить встроенную HTML-валидацию по смыслу данных;
- обрабатывать событие `submit` и останавливать перезагрузку;
- собрать актуальные значения через `FormData`;
- преобразовать значения к нужным типам, если модель содержит числа или логические значения;
- отправить объект методом `POST`;
- передать `Content-Type: application/json` и тело через `JSON.stringify`;
- проверить `response.ok` и обработать ошибку;
- блокировать повторную отправку, пока запрос не завершен;
- очистить форму только после успешного ответа;
- после успеха снова получить коллекцию с сервера или корректно добавить серверный ответ в интерфейс.

Не назначайте `id` вручную для нового объекта, если его создает `json-server`.

Проверка: отправьте две разные корректные записи. Каждая должна появиться в `db.json` и интерфейсе ровно один раз. При остановленном API введенные данные не должны молча исчезать.

### 5. Качество интерфейса и кода — до 0,5 балла

Этот критерий не создает штрафов — он награждает аккуратно завершенную работу.

- функции разделены по задачам: запрос, отображение, смена состояния и отправка формы не смешаны в один большой обработчик;
- повторяющиеся значения вынесены в константы;
- ошибки понятны пользователю, а технические детали доступны в Console;
- имена функций, переменных и CSS-классов передают смысл;
- новые классы продолжают БЭМ-структуру стартовой страницы;
- форма доступна с клавиатуры, а динамический статус объявлен через `aria-live`;
- страница остается читаемой на узком экране и с длинными значениями.

### 6. Git и воспроизводимый запуск — до 0,5 балла

#### История Git — до 0,25 балла

- сделано не менее четырех содержательных коммитов;
- сообщения отражают результат этапа, например `feat: add API resource`, `feat: render collection`, `feat: submit new event`, `fix: handle failed request`;
- вся работа не спрятана в одном финальном коммите.

#### Запуск другим человеком — до 0,25 балла

- в Git есть `package.json`, `package-lock.json` и `db.json`, но нет `node_modules`;
- корневой `README.md` обновлен под выбранную тему и endpoint;
- после `npm ci` и `npm run dev` API запускается без ручного исправления файлов;
- frontend работает через Live Server по инструкции.

GitHub Pages не обязателен: локальный `json-server` нельзя опубликовать на Pages вместе со статическим frontend. Публикация полноценной версии с удаленным API может быть самостоятельным дополнительным улучшением.

## Дополнительная часть — до 5 баллов

Сначала завершите обязательный сценарий. Дополнительные баллы начисляются только за работающие возможности, которые встроены в общий интерфейс и не ломают базу.

Улучшения разделены на три уровня. Максимум нельзя набрать количеством мелких функций одного типа: для 10 баллов нужно и развить REST-сценарий, и самостоятельно исследовать новый механизм, и аккуратно соединить результаты.

### Уровень A. Развитие REST-сценария — до 2 баллов

Материалы приложения к презентации дают отправную точку, но модель, интерфейс и пограничные случаи нужно продумать самостоятельно.

#### A1. Серверная фильтрация или сортировка — +0,75 балла

- выбор пользователя меняет query-параметры запроса, а не только скрывает уже загруженные DOM-элементы;
- параметры формируются из актуальных значений интерфейса;
- загрузка, пустой результат и ошибка продолжают работать;
- есть понятный способ сбросить фильтр или сортировку.

#### A2. Удаление ресурса — +0,75 балла

- конкретная карточка отправляет `DELETE` на endpoint с `id`;
- случайное удаление предотвращено подтверждением или отдельным понятным действием;
- кнопки защищены от повторного запроса;
- успешное удаление обновляет коллекцию, ошибка не удаляет карточку только визуально.

#### A3. Редактирование через `PATCH` — +1,25 балла

- существующая запись открывается в режиме редактирования с текущими значениями;
- измененные свойства отправляются методом `PATCH` на endpoint с `id`;
- пользователь может отменить редактирование;
- после успеха интерфейс и `db.json` показывают одинаковые данные;
- ошибка сохраняет введенные значения и дает повторить действие.

#### A4. Свое прикладное расширение — до +1 балла

Можно предложить другую законченную возможность на знакомых инструментах. Еще одно поле, декоративный эффект или копия существующей кнопки отдельным улучшением не считаются.

За весь уровень A начисляется не более 2 баллов.

### Уровень B. Самостоятельное исследование — до 2 баллов

Здесь ожидается работа с документацией и новым механизмом. Нужно уметь объяснить выбранный API и показать его поведение в обычном и проблемном сценариях.

#### B1. Поиск с debounce и отменой запроса — +1,5 балла

- запрос выполняется после паузы во вводе, а не на каждый символ;
- предыдущий незавершенный запрос отменяется через `AbortController`;
- отмена не показывается пользователю как обычная ошибка;
- запоздавший ответ не заменяет более новый результат;
- студент может объяснить таймер, `signal` и причину отмены.

Справка: [AbortController на MDN](https://developer.mozilla.org/en-US/docs/Web/API/AbortController).

#### B2. Оптимистическое изменение с откатом — +1,5 балла

- выбранное действие сразу отражается в интерфейсе;
- параллельно отправляется реальный запрос к API;
- при успехе сохраняется серверный результат;
- при ошибке интерфейс возвращается к предыдущему состоянию и сообщает причину;
- повторные действия не создают дубликаты и не теряют данные.

В качестве действия можно использовать создание, удаление, изменение статуса или другой подходящий вашей модели сценарий.

#### B3. Ограничение времени ожидания — +1 балл

- запрос отменяется через выбранный интервал с помощью `AbortController`;
- таймер всегда очищается после завершения запроса;
- тайм-аут отличается в интерфейсе от ответа `404` или остановленного API;
- повторная загрузка после ошибки остается рабочей.

#### B4. Свое исследовательское расширение — до +2 баллов

Можно исследовать другой механизм, напрямую связанный с HTTP/API:

- +1 — решена одна законченная задача и автор понимает использованный API;
- +1,5 — обработаны ошибки или важные пограничные случаи;
- +2 — механизм заметно развивает продукт, устойчив к ошибкам и согласован с остальными состояниями.

Перед началом коротко согласуйте идею и способ проверки с преподавателем. Отдельный отчет писать не нужно.

За весь уровень B начисляется не более 2 баллов.

### Уровень C. Целостность решения — +1 балл

Этот балл доступен, если в проекте есть хотя бы один работающий результат уровня A и хотя бы один работающий результат уровня B.

- основной `GET`/`POST`-сценарий продолжает работать после расширений;

- быстрые повторные действия не создают дубликаты и конфликтующие состояния;
- HTTP-логика организована последовательно, endpoint и общие настройки не дублируются;
- ошибки дополнительных запросов не оставляют интерфейс заблокированным;
- автор может объяснить полный путь данных и внести небольшое изменение на проверке.

## Когда за работу ставится 0 баллов

- Работа не отправлена преподавателю до дедлайна либо содержательные изменения сделаны уже после него.
- Обнаружены признаки чужого кода или результата, созданного нейросетью и выданного за собственный.
- Студент не может объяснить свой код и принятые решения или выполнить небольшое изменение на проверке.
- Сдан почти неизмененный стартовый проект.
- Отсутствует основной сценарий взаимодействия с API: нет самостоятельной работы ни с `GET`, ни с `POST`.
- Проект невозможно запустить по содержимому репозитория, и автор не может восстановить запуск на проверке.

Частично выполненная самостоятельная работа оценивается по критериям. Неполный объем сам по себе не является основанием для 0 баллов.

## Использование ИИ

ИИ можно использовать как консультанта, но не как автора работы.

Можно:

- попросить объяснить один метод, заголовок, статус или ошибку из Console/Network;
- получить наводящую подсказку по текущему шагу;
- сравнить два подхода;
- попросить предложить проверки для уже написанного кода;
- сверить готовую работу с критериями.

Нельзя:

- просить написать готовый `frontend/script.js`;
- поручать ИИ обязательную часть или бонус целиком;
- вставлять код, который вы не понимаете и не можете изменить;
- поручать ИИ описание pull request;
- скрывать использование ИИ.

Самостоятельное исследование уровня B означает работу с документацией, а не передачу задачи ИИ. В PR достаточно честно назвать инструмент и конкретную помощь. Отдельный отчет об ИИ не нужен.
